# Design

## Context

TrueSpec already isolates document access behind `DocumentSource`, but source creation and coding-harness setup still use central enums and match statements.
The CLI exposes direct viewer, manual inbox, relink, setup, and connector commands even though the intended user journey begins in an initialized repository and continues through a paired coding harness.

OpenSpec and Markdown document IDs are adapter-independent, review state is already workspace-local, and connector operations already work while the browser is offline.
The redesign can preserve those boundaries while replacing the public orchestration layer.

## Goals / Non-Goals

**Goals:**

- Make repository initialization the only public product command.
- Keep OpenSpec and Markdown equally supported through compile-time adapter registries.
- Let one initialization install several independent coding integrations.
- Validate the complete initialization plan before writing project or global files.
- Move reusable feedback interpretation into one portable skill.
- Preserve existing review state and queued feedback across adoption.

**Non-Goals:**

- Add runtime-loaded Rust plugins or a dynamic integration marketplace.
- Allow one open review to deliver concurrently to several conversations.
- Store per-user integration choices in committed project configuration.
- Change anchor, rendering, batching, reply, or resolution semantics.
- Add an uninstall command in this change.

## Decisions

### Store versioned project source configuration

Write `truespec/config/project.json` with this initial shape:

```json
{
  "version": 1,
  "source": {
    "adapter": "openspec",
    "path": "openspec"
  }
}
```

JSON reuses the existing Serde stack and avoids another configuration parser.
The source path is workspace-relative, canonicalized during initialization, and revalidated whenever an integration starts a review.

The project configuration is suitable for version control because it describes shared documents.
Selected integrations are not stored there because they are user-local tools and different contributors may select different harnesses.

Initialization requires the current directory to contain a `.git` directory or worktree marker file.
It does not invoke Git, so TrueSpec retains a self-contained runtime.

### Use Strategy and Factory registries for sources

Keep `DocumentSource` as the runtime Strategy used by the review core.
Add a separate source-factory interface:

```rust
trait SourceAdapter: Sync {
    fn id(&self) -> &'static str;
    fn label(&self) -> &'static str;
    fn detect(&self, root: &Path) -> Detection;
    fn open(&self, root: &Path, path: &Path) -> Result<Box<dyn DocumentSource>>;
}
```

A static registry holds `OpenSpecAdapter` and `MarkdownAdapter`.
Initialization uses the registry for detection and option validation, while runtime loading resolves the stored adapter ID through the same registry.
This removes source-specific branching from the CLI and lets future built-ins add one implementation and registry entry.

OpenSpec wins automatic detection when `openspec/` exists.
Otherwise Markdown uses `.`.
Explicit `--source` and `--source-path` override detection.

### Use integration adapters and installation artifacts

Represent each coding harness through an integration Adapter:

```rust
trait Integration: Sync {
    fn id(&self) -> &'static str;
    fn label(&self) -> &'static str;
    fn artifacts(&self, context: &InstallContext) -> Result<Vec<InstallArtifact>>;
}
```

The static integration registry initially contains OpenCode.
An artifact contains its destination, generated bytes, ownership label, and replacement policy.
The OpenCode adapter contributes its plugin and global `truespec-review` skill.

Compile-time registration is intentional.
It provides extension points and isolated tests without accepting arbitrary native code into the TrueSpec process.

### Build then commit one initialization plan

Parse CLI input into an `InitRequest`, resolve it through both registries, and build an `InitPlan` containing the project configuration write and all selected integration artifacts.

Plan construction:

1. Validate the exact repository root.
2. Resolve and validate the source adapter and path.
3. Resolve distinct integration IDs.
4. Generate every destination and file body.
5. Deduplicate identical destinations and reject conflicting generated bodies.
6. Inspect all existing files and collect every conflict.

No writes occur if any validation or preflight step fails.
With a valid plan, stage each changed file beside its destination, sync it, and atomically rename it.
Matching files are preserved.
An interrupted multi-file commit can be completed by rerunning initialization because each artifact is independently idempotent.

Use a real terminal multi-select component for interactive integration selection.
For automation, `--integration` is repeatable and `--all` selects the complete registry.

### Keep internal operations hidden and versioned

The public Clap command enum exposes only `init`.
Help and version remain built in.

Keep one hidden `connector` command containing attach, viewer startup, poll, delivered, defer, and respond operations.
Move the current testing reset option under hidden viewer startup.
Remove the public manual inbox and relink commands.
Connector subcommands retain protocol version checks and structured JSON output.

Without a public relink operation, moved files remain missing and keep their historical evidence.
TrueSpec does not infer identity from matching content or automatically attach history to a new path.

The OpenCode plugin invokes hidden connector operations through the absolute binary path installed by initialization.
Attachment reads `project.json`; it no longer accepts or hardcodes a source selection.

### Deliver batches through a paired skill

Store the portable source at `skills/truespec-review/SKILL.md` and embed it in the binary.
Each integration adapter installs that skill in its harness's global skill directory.

The skill triggers only for connector-delivered TrueSpec batches.
It owns source-context safety, current-file inspection, question versus change intent, ambiguity handling, and final response expectations.
It does not call `listen`, acknowledge leases, or record replies because the connector owns those operations.

The OpenCode queued message becomes one skill invocation plus the immutable batch JSON.
This removes repeated operational prose without hiding batch evidence.

### Remove unpaired browser handoff

Every browser review now originates from an initialized integration, so the Review panel no longer renders **Agent not listening?**, copied manual prompts, or standalone delivery guidance.
Queued and ended states continue to explain that the paired connector may deliver remaining work.

### Adopt outstanding manual batches transactionally

When the first initialized connector attaches to an existing open review, update incomplete connector-free batches in one SQLite transaction:

- Assign the new connection ID.
- Clear manual lease tokens and expiry values.
- Preserve batch IDs, immutable item snapshots, attempt history, completed items, replies, and chronological feed entries.
- Leave fully handled batches untouched.

The connector then leases only outstanding items in original submission order.
This intentionally replaces the old rule that pre-pairing batches remain in the manual inbox and prevents feedback from becoming unreachable after the public manual commands disappear.

## Risks / Trade-offs

- **Removing public commands breaks existing scripts** -> Make the breaking change before a stable release, document the new workflow, and keep protocol operations available only to integrations.
- **A source registry can become an unnecessary abstraction with two entries** -> Keep it compile-time and minimal; it removes existing branching and directly supports the requested extension boundary.
- **Multi-integration installation can partially fail during file renames** -> Preflight the complete plan and make each artifact idempotent so rerunning repairs an interruption.
- **A committed source path becomes invalid after repository changes** -> Revalidate configuration at every review start and direct the user back to `truespec init`.
- **A selected integration skill is deleted outside TrueSpec** -> Re-running initialization detects and repairs missing generated artifacts.
- **Legacy manual work is delivered again after adoption** -> Preserve completed item markers and retain at-least-once semantics only for outstanding items.

## Migration Plan

1. Existing repositories run `truespec init` from their canonical root.
2. Initialization detects or accepts their existing source configuration without deleting review state.
3. Selected integrations install their plugin and skill artifacts.
4. The first integration attachment adopts outstanding connector-free batches and opens the existing review.
5. Existing version 4 databases need no schema migration.

Rollback before stable release requires using the previous binary.
The versioned project configuration is ignored by the previous binary, while the review database and source documents remain compatible.
